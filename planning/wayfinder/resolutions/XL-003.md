# Verify harness waiting, delivery, and resumption capabilities

Primary-source findings: [Harness waiting, delivery, and resumption research](../../research/harness-compatibility.md)

## Answer

**Verified fact:** Claude Code, Codex CLI, Pi, and OpenCode all support local file/command work, command results, persisted or resumable sessions, and repository guidance. Shared local CLI is feasible; MCP is not required for MVP.

**Verified limitation:** indefinite automatic feedback waiting is not portable. Pi foreground shell has no default timeout. OpenCode defaults to two minutes but permits explicit/configured timeout. Claude Bash defaults to two minutes and normally caps at ten minutes, then backgrounds command; current Claude Monitor/background sessions provide a stronger optional event path. Codex yields long commands after ten seconds and exposes bounded `write_stdin` polling, but ordinary background completion is not verified to trigger a new model turn.

Use capability profiles:

1. Foreground `xenon wait` where one shell call can remain active long enough; arrival returns as tool result and current turn continues.
2. Optional harness event adapter only when verified to wake exact originating session without model polling: Claude Monitor/background-session guidance, OpenCode server/plugin, Pi extension/RPC, or later-proven Codex hook/app-server path.
3. Universal manual fallback: persist batch, display exact session ID and resume command, resume originating conversation, then run `xenon receive --session <id>`.

A completed background process is not agent resumption unless harness injects result or starts a new turn. Timeout, exit, shutdown, and missing automatic wake must leave feedback stored and recoverable. No universal compatibility claim is justified until versioned smoke tests prove one complete loop per harness.
